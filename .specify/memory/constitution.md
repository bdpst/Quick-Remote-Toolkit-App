# Quick Remote Toolkit App Constitution

## Core Principles

### I. Текущая Windows-сессия и защита данных

Все удалённые действия ДОЛЖНЫ выполняться от текущей Windows-сессии пользователя.
Приложение НЕ ДОЛЖНО запрашивать, сохранять или передавать пароли. Добавление хранения
учётных данных допускается только после отдельного решения по безопасному хранению
и согласованного изменения этого принципа. Требования к правам и сетевым службам
ДОЛЖНЫ быть явно описаны для каждой административной операции.

Реальные CSV клиентов, рабочие персональные данные и секреты НЕ ДОЛЖНЫ попадать
в репозиторий или примеры. Текст отправляемых пользователям сообщений НЕ ДОЛЖЕН
сохраняться в настройках или журнале. Локальные настройки ДОЛЖНЫ храниться
в пользовательском профиле. Это сохраняет границы полномочий Windows и сокращает
необходимый объём сохраняемых данных.

### II. Совместимость данных и предсказуемость удалённых действий

Контракт CSV `number;computer;ip;person`, разделитель `;` и чтение UTF-8 и Windows-1251
ДОЛЖНЫ сохраняться. Изменение формата ДОЛЖНО сопровождаться описанием совместимости
и способа перехода для существующих файлов.

Удалённые действия ДОЛЖНЫ использовать штатные средства Windows и явно выбранный
целевой ПК. Пользовательский ввод при построении команд ДОЛЖЕН передаваться как
данные с необходимым экранированием и проверками для конкретного интерпретатора.
Изменение поведения удалённой команды ДОЛЖНО сопровождаться ручной проверкой
аналогичной команды в PowerShell/CMD на разрешённом тестовом ПК.
Неудача ручного обращения к SMB или WinRM ДОЛЖНА учитываться при диагностике
как проблема окружения или прав, прежде чем менять приложение.

Административные операции ДОЛЖНЫ сохранять узкий заявленный эффект: например,
удаление из локальных администраторов меняет членство, а не удаляет учётную запись.
Идентификация встроенной группы администраторов ДОЛЖНА опираться на SID
`S-1-5-32-544`, чтобы результат не зависел от языка Windows.

### III. Отзывчивый и согласованный интерфейс

Новые и изменяемые длительные сетевые операции и ожидание ответа пользователя
НЕ ДОЛЖНЫ блокировать поток интерфейса. Массовая проверка доступности ДОЛЖНА
ограничивать параллелизм настройкой `ParallelPingLimit`. Операции с ограниченным
ожиданием ДОЛЖНЫ сообщать о тайм-ауте; повторный запуск изменения членства или
отправки сообщения ДОЛЖЕН быть недоступен до завершения текущей операции.

Изменения WPF-интерфейса ДОЛЖНЫ использовать общие динамические ресурсы из
`App.xaml`, палитры `ThemeService` и существующие размеры и отступы.
Каждое изменение интерфейса ДОЛЖНО проверяться в светлой и тёмной темах,
включая читаемость текста, выделение и доступность элементов управления.
Выбор темы ДОЛЖЕН сохраняться в настройках пользователя.

### IV. Проверяемые результаты и диагностируемые ошибки

Журнал ДОЛЖЕН позволять определить целевой ПК, действие, время и известный
результат или ошибку. Сообщения НЕ ДОЛЖНЫ приравнивать запуск внешнего процесса
к успешному завершению удалённого действия. Ошибки Windows ДОЛЖНЫ сохранять
доступные диагностические сведения, включая код, если API его предоставляет.

Тайм-аут изменения членства ДОЛЖЕН обозначать неизвестный результат и требовать
проверки состава группы перед повтором. Ответы на отправленное сообщение ДОЛЖНЫ
различать ОК, закрытие без подтверждения, тайм-аут и ошибку; ОК подтверждает
действие пользователя, но не гарантирует прочтение текста.
Экспорт журнала ДОЛЖЕН сохранять понятные записи; TXT остаётся форматом
по умолчанию, CSV — дополнительным форматом.

### V. Небольшие изменения и разделение ответственности

Изменения ДОЛЖНЫ иметь ограниченную цель, обозримый diff и проверяемый результат.
Модели данных ДОЛЖНЫ оставаться в `Models/`, работа с CSV, настройками,
темами и удалёнными операциями — в `Services/`, обработчики окон — координировать
ввод, вызовы сервисов и отображение результата. Новые зависимости и дополнительные
уровни архитектуры ДОЛЖНЫ обосновываться конкретной потребностью функции.

Источником правды ДОЛЖНЫ быть исходники и конфигурация сборки в репозитории.
`publish/`, временные файлы и локальные артефакты НЕ ДОЛЖНЫ коммититься.
Наличие отдельного прототипа НЕ ДОЛЖНО автоматически менять основной стек,
процесс выпуска или обещанный пользователю набор возможностей.

## Технологические и эксплуатационные ограничения

- Основное приложение — C#/.NET WPF для Windows, текущая цель проекта —
  `net10.0-windows`. Изменение платформы или целевой среды ДОЛЖНО включать
  обоснование и проверку сборки, публикации и совместимости.
- `C$` требует SMB и административных прав; WinRS и PowerShell Remoting требуют
  рабочего WinRM и соответствующих прав. Приложение НЕ ДОЛЖНО обходить эти требования.
- Настройки основной версии хранятся в
  `%AppData%\QuickRemoteToolkitApp\settings.json`.
- Локальная framework-dependent публикация требует .NET Desktop Runtime.
  Релизный архив для `win-x64` собирается GitHub Actions как self-contained
  single-file с компрессией. Trimming НЕ ДОЛЖЕН включаться без отдельной проверки
  совместимости WPF/XAML.
- Релиз создаётся пушем тега `vMAJOR.MINOR.PATCH`; сборка и упаковка определены
  в `.github/workflows/release.yml`. Версия конституции независима от версии приложения.
- `src/QuickRemoteToolkit.Win32/` содержит отдельный C++/Win32-прототип.
  Его ограничения ДОЛЖНЫ оставаться явно описанными; равенство возможностей
  с основной WPF-версией не предполагается.

## Процесс разработки и проверки

1. Перед изменением определить затрагиваемые сценарии, контракты и правила `AGENTS.md`.
   Для новой функции использовать цепочку Spec Kit: спецификация, план, задачи,
   реализация; небольшие исправления допускаются без отдельной спецификации.
2. После изменения кода выполнить сборку:
   `dotnet build .\QuickRemoteToolkit.App.sln -c Release --no-restore`.
   Если зависимости ещё не восстановлены, предварительно выполнить `dotnet restore`.
   Ошибка сборки ДОЛЖНА быть устранена или явно указана как блокирующая проверку.
3. Проверить затронутый сценарий: для CSV — обезличенные файлы обеих кодировок;
   для UI — обе темы; для удалённых команд — ручной эквивалент в PowerShell/CMD
   и обработку отказа доступа, недоступного ПК или тайм-аута по характеру изменения.
   Операции, изменяющие удалённый ПК, проверять только на разрешённых тестовых целях.
4. Автоматические тесты добавлять для существенной логики и регрессионных рисков.
   Проверки ДОЛЖНЫ оценивать наблюдаемое поведение; обязательное внедрение TDD
   или нового тестового фреймворка для каждого изменения не требуется.
5. Перед передачей результата проверить diff и `git status --short`, исключить
   реальные клиентские данные и артефакты. Указать выполненные проверки,
   непроверенные сценарии и ограничения. Сборка сама по себе не подтверждает
   работу удалённого действия.

## Governance

Конституция закрепляет обязательные принципы проекта; `AGENTS.md` содержит
операционные инструкции работы с репозиторием. Спецификации, планы и изменения
ДОЛЖНЫ проверяться на соответствие обоим документам. Выявленное противоречие
ДОЛЖНО быть явно разрешено при согласовании изменения, а не обходиться молча.

Поправка ДОЛЖНА содержать причину, затронутые принципы, влияние на существующие
сценарии и, при необходимости, план перехода. Поправки рассматриваются и принимаются
сопровождающим проекта в рамках проверки изменения. Исключения из принципов требуют
явного обоснования и принятой поправки до реализации противоречащего поведения.

Версия конституции меняется по SemVer: MAJOR — удаление или несовместимое
переопределение принципа; MINOR — новый принцип, раздел или существенное расширение
требований; PATCH — уточнение формулировок без изменения обязательств.
Дата принятия сохраняется, дата последней поправки обновляется в формате ISO.
При каждой поправке ДОЛЖЕН составляться Sync Impact Report с изменениями,
влиянием и отложенными вопросами; временный отчёт удаляется перед коммитом.

Проверка спецификации, плана и итогового diff ДОЛЖНА включать применимые принципы
и доказательства выполненных проверок. Изменение одной конституции проверяется
на структуру, полноту правил, версию и даты; сборка приложения для такой правки
не требуется.
